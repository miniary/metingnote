# 00. 개요

**MeetingNote** - 회의록 자동 정리 풀스택 웹 앱

## 문서 지도

| 파일명 | 역할 | 알 수 있는 것 |
|---|---|---|
| `00-overview.md` | 전체 안내 | 프로젝트가 무엇인지, 어떤 문서가 있고 어떤 순서로 읽는지 |
| `01-product.md` | 제품 정의 | 누가 왜 쓰는지, 해결할 문제, 핵심 기능과 범위 |
| `02-specs.md` | 기능 명세 | API(`/api/...`) · 데이터 모델(SQLite) · 입력과 출력 · 예외 처리 |
| `03-design.md` | 화면 설계 | 4개 화면의 배치 · 요소 이름 · id · 화면 사이 흐름 |
| `04-tasks.md` | 작업 계획 | 구현 순서, 할 일 목록, 완료 기준 |
| `05-conventions.md` | 코드 규칙 | 폴더 구조, 이름 짓기, 코드 스타일, 테스트(pytest) · 커밋 방식 |

## 읽는 순서

`00` > `01` > `02` > `03` > `04` > `05`

무엇을(01) 만들지 정한 뒤 어떻게 동작하는지(02), 어떻게 보이는지(03)를 정하고,
그다음 만드는 순서(04)와 지킬 규칙(05)을 본다.

## 화면

화면은 4종이다.

| 화면 | 하는 일 |
|---|---|
| 목록 | 첫 화면. 저장한 회의록을 카드로 보여 주고, 제목 · 참석자 · 기간으로 검색한다 |
| 넣기 | 녹취 파일(mp3 · wav)을 올려 받아쓰고, 요약 · 결정사항 · 할 일로 정리한다 |
| 상세 | 목록에서 카드를 누르면 뜨는 가운데 겹침 창. 제목 수정과 삭제를 한다 |
| 할 일 | 여러 회의의 할 일을 담당자 · 기한과 함께 표로 모아 본다 |

- 배치와 요소 이름은 `docs/화면구성.pdf` 를 따른다
- 요소의 `id` 는 `docs/화면구성.pdf` 에 적힌 그대로 쓴다. 바꾸거나 새로 짓지 않는다

| 요소 | id |
|---|---|
| 검색 입력 | `q` · `from` · `to` |
| 목록 칸 | `cards` |
| 넣기 폼 | `title` · `metAt` · `attendees` |
| 파일 · 본문 | `file` · `body` |
| 버튼 | `btnUp` · `btnSave` |
| 결과 세 칸 | `result` |
| 상세 창 | `modal` |
| 제목 수정칸 | `mTitle` |
| 할 일 표 | `todoBody` |

## 디자인

- UI 는 macOS 스타일로 한다

## 왜 이렇게 나누는가 - 관심사 분리

관심사 분리(Separation of Concerns)는 서로 다른 이유로 바뀌는 것들을 서로 다른 곳에 두는 원칙이다.
한 가지가 바뀔 때 고칠 곳이 한 군데로 모이고, 다른 곳은 건드리지 않아도 된다.

문서도 바뀌는 이유가 다르다.

- **무엇을 만드는가(01)** 는 제품 방향이 바뀔 때 바뀐다
- **어떻게 동작하는가(02)** 는 API · 데이터가 바뀔 때 바뀐다
- **어떻게 보이는가(03)** 는 화면 디자인이 바뀔 때 바뀐다
- **언제 무엇부터 하는가(04)** 는 일정과 진행 상황에 따라 바뀐다
- **어떻게 쓰는가(05)** 는 팀의 코드 규칙이 바뀔 때 바뀐다

한 파일에 모두 섞으면 화면 하나를 고치다 API 설명까지 건드리게 되고, 무엇이 최신인지 알기 어렵다.
나눠 두면 바뀐 이유에 맞는 파일 하나만 고치면 되고, 읽는 사람도 필요한 파일만 열면 된다.
코드에서 `backend/`(데이터 · 로직)와 `frontend/`(화면)를 나눈 것과 같은 원칙이다.
